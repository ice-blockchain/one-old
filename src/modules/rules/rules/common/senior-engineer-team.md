# Senior-engineer team orchestration

- For non-trivial builds, the Traffic One flow is capability-driven on every supported host: architect first, then only the implementer roles listed as eligible by the runtime-owned capability profile and compiled architecture contract, reviewer and tester after implementation, and shipper only on explicit deploy intent. Run eligible implementers in parallel when the compiled work units are independent; never invent a frontend, backend, browser, data, or native role for a surface the profile does not contain.
- **Maintenance exception:** when `lifecycle.phase: "maintenance"`, run `task-triage` before applying the greenfield team flow. Trivial/small work bypasses `senior-architect` and any `plan-<feature>.md`: send it directly to the owning implementation role(s) (`senior-frontend` for UI/pages/routes, `senior-backend` for server/data; both in parallel only when the bounded request truly needs both). Re-enter the architect flow only for complex cross-layer, schema/auth/migration/integration work.
- When the host supports first-class subagents, spawn Traffic One roles through the host's agent/task primitive when the orchestrator triggers. OpenCode materializes project-scoped global agents named `traffic-one-<projectHash12>-senior-*` under `~/.config/opencode/agents/`; use the matching named Task type so its local role model applies. Kilo materializes `.kilo/agents/<role>.md` as each role's contract; its supported Task path is built-in `general`, with `[t1-role: senior-<role>]` first and an immediate instruction to read the matching contract file. Kilo `general` is valid only with that Traffic One marker-and-contract protocol; never use Kilo `explore`.
- Host subagents do not inherit the parent agent's skills; each generated `agents/senior-*.md` / host profile must carry the required role contract. Include `[t1-role: senior-<role>]` in every readable spawn/continuation task record; the parser accepts it anywhere in that record.
- On Codex, every fresh Traffic One `spawn_agent` call needs stable structured identity and an explicit model pin: use the exact underscore-form task name (`quick_fix`, `senior_architect`, `senior_frontend`, `senior_backend`, `senior_reviewer`, `senior_tester`, or `senior_shipper`), the role's exact runtime-resolved `model` from the immutable run policy, and `fork_turns: "none"`. Current Codex child rollouts encrypt the spawn message at rest, so `task_name` and line-zero `session_meta.agent_role`/`agent_path` identify the role; the live hooks, not the transcript, provide the actual model evidence. Keep the matching marker in the message for cross-host compatibility, but never use a generic/default Codex task name or rely on marker visibility.
- Onboarding gating, the wizard question set/order, and the gate-clear conditions are owned by `rules/common/setup-gate.md` and `rules/common/onboarding.md`; the orchestrator does not restate or re-ask them. For new projects, do not continue spawning, planning, file writes, installs, or scaffolding while onboarding answers or the post-onboarding architecture plan gate are unresolved, and do not read, invoke, announce, or activate `create-feature`, `create-page`, `frontend-design`, `tdd-workflow`, or other implementation skills until `.traffic-one/.one.json` has `onboardingComplete: true` and the architect plan exists.
- The team is chosen during Traffic One onboarding, not afterward: the wizard's performance step auto-approves the matching team (High/Balanced ⇒ subagents) and shows the role→model line-up. Do NOT re-ask the user whether to run the subagent team after onboarding — that decision is already captured in local preferences. Do not pop a "Run team / Main agent only" confirmation, and do not hand-edit `team.approved`/`team.mode` to clear the gate (the wizard writes them).
- When onboarding is complete (`.traffic-one/.one.json` has `onboardingComplete: true`) and local preferences have `team.mode: "subagents"` with `team.approved: true`, AUTO-RUN the capability-eligible team for a non-trivial build without asking: spawn architect first, then the eligible implementer role(s) from the compiled work units, then reviewer + tester in parallel (shipper only on explicit deploy intent). A Go API, Laravel API-only app, Python script/CLI, or worker must not spawn `senior-frontend` or load browser/design skills; a frontend-only or native project must not spawn `senior-backend` unless the profile actually contains `api`, `data`, or `worker`; native UI uses its native QA adapter, never browser QA. Then immediately continue the user's original request end to end — do not stop to ask "what next?", to re-confirm the team, or to wait for further go-ahead.
- ONE live agent per role per run. A role is SPAWNED once; every later task for that role (next planned part, fix cycle, re-review, re-test) CONTINUES the same agent — on Claude via `SendMessage { to: <agentId from the spawn result>, message: <only the new task> }` (enabled by `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), on Codex via `followup_task` for the next turn on the same agent (`send_message` only reaches an agent that is still mid-flight; a follow-up runs on the parent's model and the model gate accepts that on an already-verified thread, so continuation — not a fresh spawn — is the supported path), on Cursor by RE-INVOKING the `Task` tool with `resume: <id from the spawn result>` (Cursor resumes the same subagent with context preserved; if a Cursor build exposes `agentId`, use the same id there), on Copilot by calling `task` with the recorded background `agent_id` (`name` alone creates a fresh task), on OpenCode by waiting for the existing named `senior-*` task when it is still running; current OpenCode builds do not expose a true Task resume field, so after a completed OpenCode role needs a follow-up/fix, re-spawn the same named `senior-*` agent only with `[t1-replace-agent]` plus the exact new findings inline (always `[t1-role: senior-<role>]` as the first line, omit `model`, never use built-in `general`), on Kilo by waiting for the live role and using an explicit `[t1-replace-agent]` built-in `general` task only after completion, with the first-line role marker, an immediate instruction to read `.kilo/agents/senior-<role>.md`, and no `model`, and on Windsurf/Devin Local by reading the live subagent first and using an explicit `[t1-replace-agent]` `run_subagent` profile `subagent_general` only after completion, with the first-line role marker and an immediate instruction to read `.devin/agents/senior-<role>/AGENT.md`. The spawn gate denies duplicate same-role spawns and names the live agent id (registry: `.traffic-one/runs/<runId>/agents.json`); replace an exhausted/dead/completed-no-resume agent only with the literal marker `[t1-replace-agent]` in the prompt. Rationale: every fresh spawn reloads the full rules+skills context and re-explores — context loads must scale with ROLES (~5), not with tasks (a measured build hit 17 spawns / 7 frontends where 5 agents should have served).
- Only fall back to asking when local preferences carry no team decision at all (no `team.mode`). If `team.mode: "main-agent"` (Low), do not call `run_subagent`, `Task`, `spawn_agent`, `task`, or another host subagent primitive. Perform the architect phase in this thread: write only `.traffic-one/plan.md`, required `.traffic-one/` project memory, semantic `ArchitectureInputV1`, and the architect digest. Let runtime compile architecture, verification, assignments, and work-unit bootstraps before creating any scaffold or feature source as the eligible implementation role(s); then keep the same dependency order.
- A preflight spawn that is DENIED or shows "Couldn't start" without a correlated terminal child transcript is NOT "genuinely unavailable" — RE-SPAWN the same role ONCE first. The first spawn often hits a one-time readiness deny (the gate converges materialization on the first gated call and denies-for-retry: "rerun the same agent spawn now"); Cursor shows it as "New subagent — Couldn't start". Re-issuing the spawn succeeds. A correlated terminal transcript follows the recovery rules below instead; never blindly retry its failed model, and never implement the role inline on a first spawn failure.
- **Cursor API-limit recovery:** a uniquely correlated API/usage-limit child transcript immediately retires the false-live agent and retries automatically on the next exact captured slug from that role's original tier. Never announce or attempt a fallback named only by Cursor error prose. The next model is authoritative only when Traffic One supplies its exact slug. Issue the prescribed Task without a pre-tool model announcement, and do not say the replacement is running until a real `subagentStart` proves it. If correlation is ambiguous, do not exhaust a model — use the existing 90-second corroborated grace / 270-second hard-dead timers. Highest/balanced roles require one explicit choice before the next candidate is the Composer floor: **enable** — Restore API budget for **<recommended-model>**, then reply **enable**; I’ll retry on the recommended model. / **fallback** — Proceed now on **<composer-slug>**. Cheapest roles treat Composer as normal and keep rotating. When every eligible model actually started for one role has API-limited, stop on a persistent per-role terminal marker; absent/disabled models do not count as tried.
- **Cursor model-unavailable recovery:** show the Settings choice only when the captured model list excludes the model or a runtime error explicitly ties a model to `not enabled`, `disabled`, `unavailable`, `invalid`, `unsupported`, `unknown`, or `not found`: **enable** — Open Cursor Settings → Models, enable **<failed-model>**, then reply **enable**; I’ll retry on the recommended model. / **fallback** — Proceed now on **<next-tier-slug>**. The fallback is the next exact captured candidate in the role's original tier. The choice remains run-level; **enable** clears the run's API ledger and pending decisions, while each pending role retains its own spawn/tier context.
- **Cursor generic recovery:** every other non-API failure keeps its real cause and uses normal recovery. Authentication, network, user abort/cancel, context exhaustion, and generic API failures must never be labeled "model disabled" and must never trigger Cursor Settings → Models.
- **Cursor synthetic completion:** Cursor may append a synthetic `Briefly inform the user…` background-completion request. It is not an **enable**/**fallback** decision. If the immediately preceding assistant turn already displayed the pending choice and no new tool work ran, do not call tools or repeat the options; reply at most `Awaiting your enable/fallback choice.` The run-level `model-choice-prompted` marker is not proof that the initial choice was shown and must not suppress it.
- Main-agent fallback (canonical, applies to every host/runtime): when `team.mode: "main-agent"`, or when subagents are genuinely unavailable or blocked at runtime (a re-spawn also failed, per above), keep the same phase order manually — same dependency order, mirrored `00-agent-senior-*` role contexts, used ONLY when the host genuinely exposes no callable agent facility (note: Claude, Codex, Cursor, Copilot, OpenCode, Kilo, and Windsurf/Devin Local all DO expose one — Cursor via the `Task` tool, OpenCode/Kilo via `task`, and Windsurf via `run_subagent` profile `subagent_general` plus the materialized role contract — so this never applies merely because a freshly created custom profile is not registered) — and state once that the Traffic One team is being simulated by the main agent.
- When `team.mode="subagents"`, the parent/orchestrator must not write feature source files. It coordinates only: updates run state, spawns Traffic One role agents, integrates their results, and summarizes. The architecture hook denies feature-source writes unless they come from an active allowed role session. If subagents are genuinely unavailable or blocked, ask the user to explicitly say they no longer want subagents and want Low/main-agent mode before rewriting local Traffic One preferences; `team.source="unavailable"` is not an authorization to downgrade.
- The parent's READING is scoped like its writing: in subagents mode read ONLY `senior-engineer-team.md`, `agent-handoff-digests.md`, the orchestrator skill, the plan, and the role digests. Do NOT read implementer rules (`rules/frontend/**`, `rules/backend/**`, stack cores, design/typography/SEO detail) "to review better" — the reviewer role reads those itself; every implementer rule the parent loads is duplicated context the roles already pay for.
- Agent-cap hygiene for the one-live-agent regime: keep implementer threads alive through the verify phase and after MVP/maintenance handoff so the user can keep developing in the same context. Include the caution "re-read any files OTHER roles changed since your last turn" in every continuation message (the live agent's memory of shared files may be stale). Close/archive a role thread only when the user explicitly asks, the agent is dead or explicitly replaced with `[t1-replace-agent]`, or the host's active-agent cap requires hygiene for threads this run will not message again. Replacing an exhausted/dead agent goes through the `[t1-replace-agent]` marker — never a bare duplicate spawn.
- Map each Traffic One role to the host's subagent capabilities — implementers get a writer-capable agent scoped to the runtime-compiled work unit; the reviewer is read-only. The runtime writes `.traffic-one/runs/<runId>/assignments.json` atomically from `CompiledArchitectureV1` and `VerificationContractV2`, then publishes each eligible role's `WorkUnitContractV1` and bootstrap. No parent or child may create, edit, widen, or replace that manifest. The descriptions below are the human summary:
  - `senior-architect` — writes only `.traffic-one/plan.md`, `.traffic-one/` project memory/ADRs, semantic `architecture-input-v1.json`, and its architect digest. It never creates packages, workspace/config files, Tailwind assets, barrels, assignments, or feature source.
  - `senior-frontend` — owns only outputs/allowlist in its runtime-compiled work unit (web/native UI, routing, and UI-adjacent artifacts only when eligible).
  - `senior-backend` — owns only outputs/allowlist in its runtime-compiled work unit (API/data/CLI/worker artifacts only when eligible).
  - `senior-reviewer` — read-only.
  - `senior-tester` — owned write scope test files and test infrastructure only.
  - `senior-shipper` — deploy/release only after the shipper gate is satisfied.
- Where the host exposes background-agent/task facilities, use them to run the same roles; otherwise apply the main-agent fallback above.
- Include the relevant Traffic One role instructions from `agents/senior-*.md` or a concise equivalent in every subagent prompt. On Kilo, use the built-in `general` task worker, keep the `[t1-role: senior-<role>]` first-line marker, and immediately tell it to read `.kilo/agents/senior-<role>.md`; never use `explore`.
- Every role spawn AND continuation prompt MUST include the structured marker `[t1-role: senior-<role>]` in a recognized task record. First-line placement is a template convention, not a parser requirement. On Codex the exact `task_name` plus line-zero session metadata is the strongest identity — always pass it when the spawn tool exposes the field; when the exposed spawn tool has NO `task_name` field, the first-line marker in the spawn message is the identity channel (child rollouts record the spawn prompt readably and the gates recover the role from it). Spawn senior roles from the ROOT orchestrator only — never nested from another senior child (hosts attribute nested edits to the spawning child, so the nested worker's writes to the role's files are denied).
- A UI implementer prompt includes only baselines selected by its capability
  profile and work unit. Web UI may require its existing/new i18n catalog,
  `<Trans>` with fallback for every static React child, SEO tests for changed public routes, and
  configured-backend degraded/demo states. Native UI uses native localization
  and emulator QA instead; API/CLI/worker/data profiles receive none of these
  browser/SEO instructions. A Supabase setup CTA and
  `https://traffic.io/` href regression apply only when that provider and
  missing-config web surface are present.
- When a configured web product has a missing Supabase/env surface, the UI
  implementer must provide typed product-specific demo/seed data and a useful
  degraded state. Missing configuration must not ship as blank panels or sparse
  UI. This rule is web-profile-only; API/CLI/worker/native profiles do not
  receive it.
- Do not ask for subagents on single-component, single-page, single-service, read-only audit, or small refactor tasks; route those directly to the matching specialist skill.
- If an agent already started a matching build without asking, stop at the next safe point, tell the user the gate was missed, and ask before continuing.
- Shipper remains gated: deploy/release/publish actions require explicit deploy intent, reviewer `APPROVED`, tester `TESTS_GREEN`, a passing `predeploy-security-check` stamp for the current worktree, and user confirmation in the same turn. The deploy hook denies production commands unless `lastShipperApprovalAt` is fresh (≤10 min) and `lastSecurityCheckStatus: "passed"` is fresh with a matching fingerprint.
- Project memory requests route through `project-memory`; architect owns the
  canonical semantic memory files (`product.md`, `stack.md`, `coding.md`,
  `security.md`, `known-issues.md`, API/database/deployment/environment memory,
  `.agentignore`, `agent-log.md`, and `decisions/*`). Runtime alone materializes
  `.traffic-one/rules/**`, `.traffic-one/skills/**`, and manifests. Backend
  refreshes `.traffic-one/schema.sql` after migrations, implementers put run
  notes in their handoff digests rather than `.traffic-one/agent-log.md`, and
  shipper appends `.traffic-one/deployments.jsonl`.
- Documentation requests route through `auto-documentation-generator`; architect
  owns only the semantic plan, project memory/ADRs, ArchitectureInputV1, and its
  digest; eligible implementers own runtime-assigned source/config/root docs.
  Reviewer checks docs and memory for accuracy and
  placeholder/secrets risk, and shipper verifies release-facing docs and memory
  before production deploy.
