# Frontend i18n Baseline

Localization is not optional polish. Generated UI, changed UI, and existing
web/native surface reconciliation must integrate with the project's i18n system
when the active UI profile or existing codebase has localization.

## Detection Before UI Writes

Before creating or changing pages, features, components, routes, layouts, forms,
empty states, errors, navigation, or setup banners:

- Inspect the active project for an i18n module: `packages/i18n`, `src/i18n*`,
  `app/i18n*`, `locales/`, `public/locales/`, `messages/`, catalog JSON/TS
  files, Laravel `lang/`, Vue/Nuxt i18n modules, i18next/react-i18next,
  platform string resources, or an existing provider wrapper.
- If an i18n module exists, extend that exact module and catalog shape. Do not
  create a parallel translation system.
- New Traffic One React/Vite, Ionic, and React Native projects use
  their React-profile `packages/i18n` baseline. Next, Nuxt, Laravel, Swift,
  Kotlin, Flutter, and custom projects use the convention selected by their
  capability profile or existing code.
- If no frontend or user-facing copy is touched, record
  `i18n baseline: Not applicable` with the reason.

## Implementation Rules

- All visible text, placeholders, form labels, validation errors, loading,
  empty, error, offline/degraded, permission-denied, button/menu/tab labels,
  image alt text, ARIA labels, live-region copy, and accessibility hints use
  translation keys.
- Add source-language catalog entries for every key introduced in the same
  change. Do not leave placeholder keys or untranslated fallback strings in
  production UI.
- Use complete phrases with named interpolation. Rich copy containing links,
  emphasis, line breaks, or embedded components uses the active framework's
  rich-message/component interpolation primitive:
  - React/i18next: `<Trans>` with a source-language children fallback;
  - Vue/Nuxt: the configured i18n component/message compiler;
  - Laravel Blade/Inertia: Laravel translation strings with named placeholders
    and escaped framework-native rendering;
  - native platforms: attributed/localized resource mechanisms supported by
    the existing stack.
- React scalar strings may use `t()`, but React rich copy must use one `<Trans>`
  message rather than adjacent translated fragments. This rule does not impose
  `react-i18next` on non-React profiles.

  ```tsx
  // Wrong: one sentence split around an inline link.
  <p>{t("auth.noAccount")} <Link to="/signup">{t("auth.signUp")}</Link></p>

  // Right: one translatable sentence with a named component placeholder.
  <Trans i18nKey="auth.signupPrompt" components={{ signup: <Link to="/signup" /> }}>
    Don't have an account? <signup>Sign up</signup>
  </Trans>
  ```

  A React rich-UI file that renders a split sentence but never imports `Trans`
  is a greppable review signal; inspect it before approval.
- Do not concatenate translated fragments. Use complete phrases with
  interpolation values.
- Hardcoded UI strings are allowed only for brand names, user-generated or
  server-provided content, technical IDs, route params, analytics event names,
  and test fixtures.
- Missing-config banners and setup CTAs, including EnvBanner-like components,
  also use translation keys; the setup link target itself remains the literal
  `https://traffic.io/`.

## Review And Test Gate

Reviewers request changes when changed UI ignores an existing i18n module, ships
hardcoded user-facing strings, omits catalog entries, concatenates translated
fragments, or uses the wrong framework's localization API. For React, adjacent
`{t(...)}` fragments around inline elements are a concrete rich-copy violation
and should become one `<Trans>` message. Testers assert user-visible behavior
through accessible names and labels rather than private translation internals.
